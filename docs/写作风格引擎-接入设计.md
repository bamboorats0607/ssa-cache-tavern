## 一、要接入的是什么

`deep-reply` 的能力拆成五个可迁移单元，逐项判断在本 App 里的必要性——**有一项结论是"不该接"**：

| # | 插件能力 | 本 App 是否需要 | 理由 |
|---|---|---|---|
| 1 | 四步思考引导（分析→发散→自审→起草，只输出结果） | **不接** | 本 App 已有 `enable_thinking` 参数（`chat.ts:143-172` 已在发送），"在心里执行四步"是模型 thinking 模式的低配复刻。再塞一段四步引导只会**重复占用前缀 token 并与 thinking 参数打架**。风格引擎不负责思考，只负责风格 |
| 2 | 去 AI 味风格块（节奏/闲笔/无禁清单） | **接，且默认开** | 第 1 轮结论的正面落点；对所有用户都有收益，不涉及题材尺度 |
| 3 | 风格样本锚定（few-shot） | **接，可选** | 第 2 轮 §1.6：风格长在"参照物"上比长在形容词上有效；这是提示词层面最强的单一手段 |
| 4 | 成人化深度档位（许可而非要求） | **接，可选，默认关** | 与插件一致的"上限"语义：允许写到哪、不要求写到哪 |
| 5 | 文学化手法（余波/医学/证词视角） | **接，可选** | 是**呈现方式**而非尺度，与 #4 正交 |

**关键取舍**：不接 #1。这是本轮设计里唯一一处与插件行为**故意不一致**的地方——插件当年要在宿主只给一个输入框的前提下工作，本 App 有真正的思考参数，所以思考归参数、风格归风格块。

## 二、SSA 兼容性分析（为什么风格块必须进前缀）

| 红线 | 风格块如何满足 | 违反的后果 |
|---|---|---|
| **R1 前缀区字节级冻结** | 风格块由**纯函数**从设置生成，**不含时间戳/随机数/会话变量**；同一会话内输入不变 ⇒ 输出逐字节相同。用 `styleFingerprint()` 做记忆化，复用 `worldbook.svelte.ts:236-240` 那套按引用缓存的写法 | 每轮前缀变一个字节 ⇒ 整段 KV 缓存作废，长对话成本与延迟暴涨 |
| **R2 尾缀区每轮必 miss** | 风格块**不进尾缀**。唯一的尾缀候选是"关键约束短句复述"（见 §三.4），且默认关闭 | 把静态内容放进尾缀 = 每轮都重新计费，白交钱 |
| **R3 压缩必须缓存对齐** | 风格块不属于 MC 压缩对象：它是装配产物，不写进摘要；MC 折叠时前缀结构不变 | 压缩触发前缀重排 ⇒ 缓存结构性下移 |

**缓存代价与 UX**：用户**切换**风格/深度/手法/样本 ⇒ 风格块字节变化 ⇒ 前缀重建一次（一次 miss，随后恢复）。这必须**显式提示**，不然用户会以为命中率出了问题。已有现成指标可用：`chat.ts:308-319` 已经在归一化 `prompt_tokens_details.cached_tokens`，`lib/MessageBubble.svelte` 展示 `TurnStats.breakdown` —— 在设置页加一行「保存后下一轮命中率会短暂下降」即可，不需要新统计。

**位置依据**：第 2 轮 §1.4 —— 指令遵循存在序列位置效应，**开头（primacy）> 结尾（recency）> 中间**，且有 EACL 2026 的专门基准。前缀正是 primacy 区，这也是"风格块进前缀"在效果上不吃亏的原因。

## 三、设计

### 3.1 模块清单

```
app/src/lib/style/
  types.ts      DepthKey / LensKey / StyleInput 类型
  presets.ts    预设文案表（全部"正向指定"，零禁用清单）
  guide.ts      buildStyleGuide(input): string   纯函数、确定性
                styleFingerprint(input): string   会话内缓存重建判定
app/src/stores/
  writing-style.svelte.ts   KEY='tavern.writingStyle'，load()/persist()/set()
app/src/views/settings/
  WritingStylePage.svelte   设置页
```

约定照抄现有代码：store 走 `advanced.svelte.ts` 的 `KEY + load() + persist() + set()` 形状（KEY 在 `advanced.svelte.ts:15`，load/persist/reset 在 `:174-221`）；设置页用 `app/src/lib/settings/` 下几个既有壳组件（`SubPage` / `SettingGroup` / `SettingRow` / `Field` / `SettingText`），不引组件库；文案直接写中文（本仓**没有 i18n 层**，`index.html:2` 就是 `lang="zh-CN"`）。

### 3.2 数据形状

```ts
// lib/style/types.ts —— 实际实现（4 个控件，比初稿少一个）
export type DepthKey = 'none' | 'mature' | 'explicit' | 'transgressive';
export type LensKey  = 'direct' | 'aftermath' | 'medical' | 'testimony';

export interface StyleInput {
  register: boolean;    // 聊天体（对话 + 叙述两段），默认 true
  depth: DepthKey;      // 尺度上限，默认 'none'
  lens: LensKey;        // 呈现视角，默认 'direct'
  sample: string;       // 风格样本（真人文本），默认空
}
```

**为什么比初稿少了 `style` 预设档（plain/expert/casual/story/blunt）**：那套档位是给「一个输入框的插件」用的；本 App 里**角色卡已经定义说话人是谁**，再叠一层全局风格档会与角色卡抢话语权。所以只保留三件角色卡管不到的事：**聊天体语体**（怎么说）、**尺度上限**（能写到哪）、**视角**（从哪儿下笔），加上**样本**。

**为什么默认只开 `register`**：聊天体对本 App 的用例（酒馆 = 聊天 + 描写）几乎纯收益且不涉尺度；尺度与视角属个人偏好，默认不注入。默认态下生成的块 = 聊天体两段，其余为空。

### 3.3 注入点（唯一改动点）

`app/src/lib/chat-context.ts:142` —— 在角色块之后、`【世界设定·恒定】` 之前，插入一条 system 轮：

```ts
// chat-context.ts，紧邻 :142 的 if (r.layers.prefix.length > 0) 之前
const guide = input.styleGuide;              // 由调用方从 store 生成后传入（lib 保持纯净）
if (guide) {
  messages.push({ role: 'system', content: guide });
}
```

三条刻意的选择：

1. **插在角色块之后**，不是最前面：群聊断言（见 §四.1）要求群聊 head 必须是第一条 system；放在角色块之后既满足断言，又保住"角色身份优先于文风"的语义。
2. **lib 不读 store**：`buildContext` 现有签名是纯函数式的，风格块作为输入字段传入，读取发生在调用点 `ChatView.svelte:407-423 turnsFor()`。这样 lib 可单测、`verify:determinism` 能覆盖。
3. **只加一条 system 轮**，不合并进世界书前缀：世界书前缀由 `assembleContext` 决定内容与顺序，风格块与它解耦后互不干扰，MC 压缩也不碰它。

### 3.4 可选：尾缀复述（默认关）

若实测发现风格约束在中后段失效（长回复尤甚），可在 `chat-context.ts:175-180` 的尾缀块之后追加一行短句（如「记住：不总结、不升华，说完就停」）。代价是每轮几十 token，**不影响前缀缓存**。第 2 轮 §1.4 支持这个做法（primacy + recency 双覆盖），但本轮**不做为默认**——先验证前缀版本是否够用。

### 3.5 token 预算

用现成的 `estimateTokens()`（`assembler.ts:170`）约束风格块：**风格块 + 样本 ≤ 500 tokens**（`GUIDE_TOKEN_BUDGET`），设置页实时显示估算值并给出上限提示。理由：风格块进前缀，长对话里它会乘以轮数反复计费（缓存命中价低但非零）；样本超长时的边际收益远小于成本。

### 3.6 门禁（验收标准）

新增 `app/e2e/writing-style.spec.ts`（照 `group-chat.spec.ts` 的写法：`page.route` 打桩后端 + 种 `localStorage`）：

| # | 断言 | 目的 |
|---|---|---|
| G1 | 风格块出现且**仅出现一次**，位置在角色块之后、世界设定之前 | 注入点正确 |
| G2 | 连续两轮请求，**前缀部分的 messages 逐字节相同**（`JSON.stringify` 全等），差异只出现在新增历史与尾缀 | **R1 红线**（最关键的回归门禁） |
| G3 | `register=false` 且各档位为默认时，**不产生**风格块 | 默认态干净 |
| G4 | 群聊场景 head 仍是第一条 system | 保护既有断言（`group-chat.spec.ts:1-19`） |
| G5 | 同一 `StyleInput` → 同一字符串（含样本换行归一化） | 确定性，接 `verify:determinism` |

## 四、与现有代码的三个冲突（必须先处理）

### 4.1 群聊断言会被插入位置破坏

`app/e2e/group-chat.spec.ts:1-19` 断言群聊 head 是**第一条** `system` 消息。风格块若插在 head **之前**，该测试立刻红。→ 设计上把风格块固定在**角色块/群聊 head 之后**（§三.3），断言无需改动。

### 4.2 四个参数在 UI 里，但根本没发出去 —— ✅ 已处理（2026-09-14）

`model.svelte.ts:14-52` 有 `topK / minP / repPen / seed`，`ModelPage.svelte:18-26,103-116` 把它们画出来了，但 `buildBody()` 只映射 `temperature / frequency_penalty / presence_penalty / top_p / max_tokens / stream / enable_thinking`。

**上游取证之后，四个参数并不同命**（`server-ref/src/endpoints/backends/chat-completions.js`）：

| 参数 | custom 源能否到达模型 | 依据 |
|---|---|---|
| `top_k` | ✅ 能 | 最终共用请求体（3470 行）`'top_k': top_k > 0 ? top_k : undefined` |
| `seed` | ✅ 能 | 同一处 `'seed': request.body.seed`，无门控 |
| `min_p` | ❌ 不能 | 只出现在 NANOGPT 等分支的 `bodyParams`（3294/3300），共用体里没有 |
| `repetition_penalty` | ❌ 不能 | 同上 |

所以"补进 `GenerateOptions` 与 `buildBody`"只对前两个成立，对后两个是**假修复**（发了会被静默丢弃）。落地做法：

- `top_k` / `seed` 直接下发，且**只在偏离默认值时**才带（`top_k > 0`、`seed !== -1`），保证默认请求体逐字节不变；
- `min_p` / `repetition_penalty` 走 `custom_include_body`（3235 行 → `util.js:868 mergeObjectWithYaml`）。注意它按 **YAML 字符串**解析，传对象会被 try/catch 吞掉——这是最容易踩的坑；
- 因为强制下发要求端点自身认识这两个字段（否则可能 400），它由一个**默认关**的开关 `forceSamplers` 控制，设置页文案写明代价；
- **不要**顺手把它们当"去 AI 味"的调优手段：第 2 轮 §1.2 温度与连贯性无关、与不连贯相关；§1.3 惩罚类参数不能稳定抑制重复且会降质。风格只能来自提示词与样本；
- `ChatView` 两处重复的 `GenerateOptions` 已抽成 `requestOptions(signal)`，并用 `satisfies Omit<GenerateOptions,'messages'|'charName'>` 锁住字段名（打错字就是编译错）。

### 4.3 `advanced` 里已有一套惰性提示词字段，别再造第三套

`advanced.svelte.ts:67-75` 有 `syspromptEnabled / syspromptContent / syspromptPostHistory / personaDescription…`，UI 也在（`InstructPage.svelte`、`PersonaPage.svelte`），但**生成链路里没有任何地方消费它们**（`ChatView.svelte` 根本没 import `advanced`）。

因此：风格块**不要**塞进 `syspromptContent` 并把那套一并激活——那会把"未接线"变成"接线范围失控"。二者边界写清：

- `advanced.sysprompt*` = SillyTavern 兼容语义的系统提示（未来要做的是**接线**，不是复用）；
- `writingStyle` = 本 App 自有的风格层，独立 store、独立前缀槽位，**不写世界书、不写 summaries**。

## 五、分期

**Phase 1 · 核心 —— ✅ 已完成（2026-09-14）**
`types.ts` / `presets.ts` / `guide.ts` + store + 注入点 + 设置页（register / depth / lens / sample 四个控件）+ 门禁。

**Phase 2 · 风格样本**
`sample` 输入（限长 + 换行归一化 + 会话内冻结）+ 缓存重建提示 + token 估算显示。
验收：样本变化 ⇒ 一轮 miss，随后恢复；样本为空 ⇒ 与 Phase 1 输出逐字节一致。

**Phase 3 · 参数打通 —— ✅ 已完成（2026-09-14）**
`topK` / `seed` 直接下发（仅偏离默认值时带）；`minP` / `repPen` 走 `custom_include_body` 逃生口（默认关，见 §四.2）；`ChatView` 两处构造抽成 `requestOptions(signal)`。
**验收实测**：`topK=40 / seed=12345` → 请求体含 `top_k: 40` / `seed: 12345`；开 `forceSamplers` → `custom_include_body` 是 YAML 字符串 `min_p: 0.05↵repetition_penalty: 1.1`；默认值 → 请求体**不含**这三个键（与改动前逐字节一致）。
**没做的部分**："生成后压缩自检"（第二遍调用）不做 —— 成本翻倍，且第 3 轮结论是"短对话本来就骗得过人"，压缩自检的收益落在长文上，与本 App 主用例不符。

**Phase 4 · 端侧改写（先评估再决定）**
第 2 轮 §1.6 的 InMyStyle 路线（0.5B–7B LoRA 把 AI 文本改写向个人风格，感知 AI 味降 >20%）。**倾向不做**：内嵌后端跑在 libnode 上，模型文件与内存都会顶到 APK 体积上限；若要做，应先测 `0.5B q4` 的端侧可行性再立项。

## 六、风险与不做的事

| 项 | 判断 |
|---|---|
| 风格块与角色卡冲突 | 措辞上明确**角色卡优先**：风格块只约束"怎么说"，不覆盖"谁在说" |

| 中文措辞无实验背书 | 第 2 轮 §1.7：中文侧只有特征研究，没有"提示词干预 → 人类评分"的对照实验。文案按第 1 轮的机制结论自拟，**不谎称有论文支撑** |
| 把"不均匀"做成硬指标 | 第 1 轮已记录：硬指标会造出新的机械模式（"每段必须有个短句"）。所有节奏项一律写成**许可式**（允许/不必） |
| 不接的东西 | 四步思考引导（§一.1）、禁清单式提示词（第 1 轮 §3 的负向禁令反噬）、检测器对抗（第 1 轮 §5：提示词改不了底层分布） |
